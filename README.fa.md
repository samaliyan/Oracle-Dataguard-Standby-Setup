# راه‌اندازی خودکار استندبای فیزیکی دیتا گارد اوراکل

این برنامه یک اسکریپت بش است.
این اسکریپت روی یک سرور جدید، مرحله به مرحله، یک استندبای فیزیکی از دیتابیس اصلی می‌سازد.
اسکریپت روی سرور استندبای اجرا می‌شود.
دیتابیس با روش کپی مستقیم ریمن منتقل می‌شود.

**این اسکریپت خودبه‌خود هیچ تغییری روی سرور اصلی نمی‌دهد.**
روی سرور اصلی فقط چند بررسی ثابت و فقط‌خواندنی اجرا می‌شود.
هر کاری که لازم است روی سرور اصلی انجام شود، همراه با دستور برگرداندنش چاپ می‌شود.
بعد از اینکه ادمین آن را اجرا کرد، اسکریپت نتیجه را دوباره به‌صورت فقط‌خواندنی بررسی می‌کند.
فقط اگر در تنظیمات `PRIMARY_RUN=yes` بگذارید، یک مرحله‌ی سرور اصلی می‌تواند دستورهای یک فهرست ثابت (پارامترهای دیتا گارد، force logging، standby logها) را بعد از جواب `y` شما از راه ssh اجرا کند.

محافظ SQL فقط دستورهای خود اسکریپت را بررسی می‌کند. فایل `glogin.sql` (یا `login.sql`) روی سرور اصلی در هر ورود sqlplus اجرا می‌شود و به عهده‌ی DBA همان سرور است.

اسکریپت رمزنگاری Oracle Net را بررسی نمی‌کند. کپی ریمن و redo همان‌طور که شبکه‌ی Oracle شما تنظیم شده منتقل می‌شوند.
اگر شبکه‌ی بین دو سرور قابل اعتماد نیست، پیش از کپی رمزنگاری بومی شبکه (`SQLNET.ENCRYPTION_SERVER` و `SQLNET.ENCRYPTION_CLIENT` در `sqlnet.ora` هر دو سرور) یا TCPS را راه بیندازید.

## پشتیبانی

1. نسخه‌های اوراکل از ۱۲.۱ تا ۲۳ (نسخه‌های جدیدتر پذیرفته نمی‌شوند)
2. اوراکل لینوکس نسخه‌های ۷ و ۸ و ۹ روی سرور استندبای
3. ذخیره‌سازی روی ای‌اس‌ام، روی فایل‌سیستم، یا هر دو
4. گرید با کاربر جداگانه یا با همان کاربر اوراکل

هر نسخه روی هر لینوکسی نصب نمی‌شود (مرحله‌ی ۱.۶ پیش از هر نصبی این را بررسی می‌کند):

1. نسخه‌های ۱۲.۱ و ۱۲.۲ و ۱۸ فقط روی اوراکل لینوکس ۷
2. نسخه‌ی ۱۹ روی اوراکل لینوکس ۷ و ۸؛ روی ۹ فقط همراه با Release Update نسخه‌ی ۱۹.۱۹ یا جدیدتر (تنظیم `RU_DIR`)
3. نسخه‌ی ۲۱ روی اوراکل لینوکس ۸؛ روی ۹ فقط همراه با Release Update نسخه‌ی ۲۱.۱۲ یا جدیدتر
4. نسخه‌ی ۲۳ روی اوراکل لینوکس ۸ و ۹

نسخه‌های ۲۱ و ۲۳ هنوز پشتیبانی کامل ندارند: خانه‌ی اوراکل در این نسخه‌ها فقط‌خواندنی است و مرحله‌ی ۳.۸ آنجا متوقف می‌شود.

## دانلود

فایل اسکریپت هر نسخه در صفحه‌ی Releases همین مخزن است، با نامی مثل این:

```
dg_standby_setup-5.33.sh
```

کنار آن یک فایل sha256 هم هست برای بررسی سالم بودن فایل. تغییرهای هر نسخه در این فایل است:

```
CHANGELOG.md
```

## شروع کار

اسکریپت را روی سرور استندبای کپی کنید و با کاربر روت اجرا کنید.

اول فقط بررسی، بدون هیچ تغییری:

```bash
./dg_standby_setup.sh --check
```

در اولین اتصال، اسکریپت اثر انگشت کلید اس‌اس‌اچ سرور اصلی را نشان می‌دهد.
پیش از تأیید، آن را با خروجی این دستور روی سرور اصلی، با کاربر روت، مقایسه کنید:

```bash
for f in /etc/ssh/ssh_host_*_key.pub; do ssh-keygen -lf "$f"; done
```

اگر یکی نبودند، تأیید نکنید و اول علت را پیدا کنید.

ساختن استندبای:

```bash
./dg_standby_setup.sh
```

اگر اسکریپت بدون هیچ گزینه‌ای اجرا شود، اول یک منو نشان می‌دهد.
در منو می‌توانید کل کار را انتخاب کنید، یا فقط یک بخش را.
برای نمونه فقط آماده‌سازی سیستم‌عامل، فقط نصب گرید، فقط نصب نرم‌افزار دیتابیس، یا چند مرحله‌ی دلخواه.
اسکریپت بعد از آخرین مرحله‌ی آن بخش متوقف می‌شود.

```
  Setup
   1) Full setup
   2) Check only, change nothing
   3) OS preparation only (phase 2)
   4) Grid Infrastructure and ASM only
   5) Database software only
   6) Primary changes for the DBA (phase 4)
   7) Choose steps
   8) Start from a step

  After setup
   9) Health check
  10) Roll forward the standby from the primary

  Information
  11) Status of every step
  12) Changes made, and undo
  13) The manual way of a step
  14) Settings
```

همین بخش‌ها از خط فرمان هم اجرا می‌شوند:

```bash
./dg_standby_setup.sh --only os
./dg_standby_setup.sh --only grid
./dg_standby_setup.sh --only db
./dg_standby_setup.sh --only 2.1-2.4
```

پیش از هر مرحله، اسکریپت نشان می‌دهد چه چیزی پیدا کرده و چه کاری می‌خواهد بکند. بعد با این گزینه‌ها از شما می‌پرسد:

```
[y] Yes, do it   [a] Yes to all   [s] Skip   [h] Help   [q] Quit
```

## راهنمای کامل فرمان‌ها

همه‌ی فرمان‌ها را با کاربر root و روی سرور استندبای اجرا کنید. هم‌زمان فقط یک اجرا ممکن است. هیچ‌کدام چیزی را روی سرور اصلی تغییر نمی‌دهد.

### ۱. اجرای بدون گزینه

```bash
./dg_standby_setup.sh
```

یک منو در سه گروه باز می‌شود. کنار هر گزینه، گزینه‌ی خط فرمانِ همان کار به رنگ کم‌رنگ نوشته شده است.
در اجرای بعدی از همان جایی ادامه می‌دهد که متوقف شده بود. مرحله‌های انجام‌شده فقط دوباره بررسی می‌شوند.

بعد از فاز ۱ یک صفحه‌ی خلاصه می‌آید: آنچه روی سرور اصلی و این سرور پیدا شد، محل هر نوع فایل، برنامه‌ی کار، مشکل‌های همین حالا، و مقدارهای این اجرا با شماره.

در حالت صفحه‌ای، مقدارها با صفحه‌کلید هم انتخاب می‌شوند: کلیدهای بالا و پایین یک نشانگر را روی مقدارها جابه‌جا می‌کنند، Enter مقدار نشان‌شده را تغییر می‌دهد و Esc نشانگر را برمی‌دارد (آن‌وقت Enter اجرا را شروع می‌کند).
مقدارهایی که چند جواب مشخص دارند (محل فایل‌های دیتابیس و recovery area، روش دیسک‌های ASM، پاک‌سازی آرشیولاگ‌ها) یک صفحه‌ی انتخاب باز می‌کنند که گزینه‌ها را با توضیحشان نشان می‌دهد.
تایپ شماره و تایپ مقدار مثل قبل کار می‌کند.
منوی شروع هم یک صفحه است: با بالا و پایین گزینه را انتخاب و با Enter اجرا کنید، یا شماره‌اش را تایپ کنید. روی ترمینال کوچک، صفحه‌ی خلاصه همراه نشانگر جابه‌جا می‌شود و همه‌ی مقدارها در دسترس‌اند.
با زدن شماره‌ی هر مقدار فقط همان پرسیده و ذخیره می‌شود. با Enter کار شروع می‌شود.

هر مرحله دستورهای دقیقی را که اجرا می‌کند زیر عنوان زیر نشان می‌دهد:

```
Will run
```

و بعد می‌پرسد:

```
[y] Yes, do it   [a] Yes to all   [s] Skip   [h] Help   [q] Quit
```

هنگام اجرا هم هر دستور یک بار دیگر نشان داده می‌شود و در لاگ کامل ثبت می‌شود.
دستورهای سرور اصلی فقط نشان داده می‌شوند. شما آن‌ها را آن‌جا اجرا می‌کنید، r می‌زنید و اسکریپت نتیجه را بررسی می‌کند.
اگر در تنظیمات مقدار زیر را بگذارید، مرحله‌های سرور اصلی پیشنهاد می‌دهند دستورهای مجاز را خودشان از راه ssh اجرا کنند (هر مرحله با پرسیدن):

```
PRIMARY_RUN=yes
```

### ۲. فقط بررسی

```bash
./dg_standby_setup.sh --check
```

همه‌ی بررسی‌ها را انجام می‌دهد و می‌گوید چه چیزی کم است. هیچ چیزی را در Oracle، سیستم‌عامل یا سرور اصلی تغییر نمی‌دهد و پیشرفت ذخیره‌شده را هم دست نمی‌زند.
رمز ssh و رمز sys را می‌پرسد، چون باید سرور اصلی را بخواند.
سرعت شبکه را اندازه نمی‌گیرد (این آزمایش ۶۴ مگابایت از سرور اصلی می‌فرستد)؛ اجرای عادی پیش از کپی آن را اندازه می‌گیرد.
روی سرور تازه اول همین را اجرا کنید.

### ۳. دادن آدرس سرور اصلی و کاربر ssh

```bash
./dg_standby_setup.sh --primary 10.0.0.5 --user oracle
```

آدرس یا نام سرور اصلی و کاربر ssh آن را می‌دهد تا این دو سؤال پرسیده نشود. کاربر پیش‌فرض oracle است و root پذیرفته نمی‌شود.

### ۴. ادامه از یک مرحله

```bash
./dg_standby_setup.sh --from 6.1
```

از مرحله‌ی داده‌شده تا آخر پیش می‌رود. فاز ۱ (اتصال و تنظیمات) همیشه اول اجرا می‌شود.

### ۵. اجرای فقط یک بخش

```bash
./dg_standby_setup.sh --only 4
./dg_standby_setup.sh --only grid
./dg_standby_setup.sh --only 2.1-2.4
```

فقط همان بخش را اجرا می‌کند و بعد از آخرین مرحله‌اش می‌ایستد. فاز ۱ اول اجرا می‌شود، پس سرور اصلی باید در دسترس باشد. مقدارهای مجاز:

- شماره‌ی یک فاز. فاز ۴ کارهای سرور اصلی است و فاز ۱۰ بررسی سلامت.
- مقدار os یعنی فاز ۲.
- مقدار grid یعنی مرحله‌های ۳.۱ تا ۳.۵.
- مقدار db یعنی مرحله‌های ۳.۶ تا ۳.۱۱.
- مقدار primary یعنی فاز ۴.
- یک مرحله یا یک بازه، مثل این‌ها:

```
3.6
2.1-2.4
2-3
```

### ۶. اجرا بدون پرسیدن تک‌تک کارها

```bash
./dg_standby_setup.sh --yes
```

برای کارهای همین سرور خودش y می‌زند. این موارد همیشه پرسیده می‌شوند: پاک‌کردن دیسک، کنار گذاشتن فایل‌های باقی‌مانده، پوشه‌ی نرم‌افزار نیمه‌کاره، کپی دیتابیس (کلمه‌ی DUPLICATE)، کلید سرور اصلی، رمزها، راه‌اندازی دوباره‌ی listener، مرحله‌هایی که استندبای را دوباره راه می‌اندازند، و تنظیم پاک‌شدن archived log ها.
روش معمول: اول بررسی، بعد گذاشتن فایل‌های zip نصب سر جایشان، بعد همین فرمان.

**فایل‌های نصب:** فایل‌های zip مربوط به grid و database را کنار خود اسکریپت بگذارید. پوشه‌های /stage، /software، /install، /u01، /opt، /root، /home، /tmp، /mnt و /media هم تا سه سطح پایین‌تر جست‌وجو می‌شوند.
- نسخه از اسم فایل خوانده می‌شود (مثل `LINUX.X64_193000_db_home.zip`). اگر اسم فرق داشته باشد، مثل فایل‌های edelivery (`V982063-01.zip`) یا فایلی که اسمش را عوض کرده‌اید، نسخه از داخل zip خوانده می‌شود. grid یا database بودن هم از داخل zip معلوم می‌شود. فقط فایل هم‌نسخه با primary استفاده می‌شود، پس نسخه‌های دیگر در همان پوشه مشکلی ایجاد نمی‌کنند.
- مالک فایل باید root یا oracle یا grid باشد و فقط مالک بتواند آن را تغییر دهد (مثلاً `chmod 644`). اگر این‌طور نباشد، فایل استفاده نمی‌شود و دلیلش نشان داده می‌شود.
- نسخه‌ی 12.1 دو فایل است و اسمشان باید با `_1of2.zip` و `_2of2.zip` تمام شود.
- Release Update و OPatch خودکار پیدا نمی‌شوند. اگر primary پچ داشته باشد، مرحله‌ی 3.1 این را می‌گوید و در صفحه‌ی خلاصه مقدار «Release Update» را تنظیم می‌کنید: `RU_DIR` پوشه‌ی unzip شده‌ی RU است و `OPATCH_ZIP` فایل `p6880880_*.zip`.

صفحه‌ی خلاصه (مرحله‌ی 1.4) فایل‌های پیداشده را در خط «Installer zips» نشان می‌دهد.

### ۷. دیدن و ویرایش تنظیمات

```bash
./dg_standby_setup.sh --settings
```

صفحه‌ی خلاصه و مقدارهای تنظیمات را نشان می‌دهد، بعد می‌ایستد. با شماره هر مقدار را تغییر می‌دهید، یا با e فایل تنظیمات را باز می‌کنید.
تنظیم‌های تازه: محل فایل‌ها، اندازه‌ی recovery area، تعداد channel ها، و روش پاک‌کردن archived log ها:

```
DATA_DEST   FRA_DEST   FRA_SIZE   PRIMARY_CHANNELS   AUX_CHANNELS
ARCH_CLEANUP=timer|crontab|oracle|none   ARCH_CLEANUP_TIME=04:30   ARCH_CLEANUP_DAYS=1
```

### ۸. وضعیت همه‌ی مراحل

```bash
./dg_standby_setup.sh --status
```

اول یک بخش کوتاه از وضعیت Data Guard نشان می‌دهد: نقش (role) و حالت باز بودن دیتابیس، protection mode، وضعیت redo apply (یعنی MRP)، lag انتقال و apply، و آخرین log اعمال‌شده برای هر thread.
اگر instance استندبای روی همین سرور بالا باشد، این مقدارها همان لحظه و فقط با خواندن گرفته می‌شوند. وگرنه مقدارهایی نشان داده می‌شود که آخرین اجرای بررسی سلامت یا فاز ۱۰ ثبت کرده، همراه با زمانشان.
بعد می‌گوید آخرین بار کی بررسی سلامت و فاز ۱۰ اجرا شده‌اند (با نتیجه و فایل لاگ). بعد نتیجه‌ی هر فاز، و هر مرحله را با نتیجه، زمان اجرا و برای مرحله‌ای که انجام نشده، علتش.
در آخر هم اجراهایی را که این نتیجه‌ها را ثبت کرده‌اند، با مسیر فایل لاگ هر کدام، فهرست می‌کند.
هرگز به سرور اصلی وصل نمی‌شود، پس وقتی سرور اصلی خاموش است هم کار می‌کند.

### صفحه‌ی برنامه

در ترمینالی که دست‌کم ۸۰ ستون و ۲۴ خط دارد، بالای صفحه یک نقشه‌ی ثابت است: هر فاز با تعداد مرحله‌های انجام‌شده از کل، فاز فعلی، و جمع کارهای انجام‌شده، نیازمند توجه و مانده.
زیر آن فقط مرحله‌ی فعلی نشان داده می‌شود. مرحله‌های قبلی همان فاز هر کدام یک خط هستند و هشدارهایشان زیرشان می‌آید.
تلاش دوباره‌ی یک مرحله روی صفحه‌ی تمیز شروع می‌شود.
نصب‌کننده‌ها، اسکریپت‌های root و کپی RMAN فقط یک خط زنده نشان می‌دهند: چه چیزی اجرا می‌شود و چقدر گذشته. خروجی کاملشان در فایل خودش می‌ماند.

کلیدهایی که جلوی هر سؤال کار می‌کنند:

```
l   فهرست همه‌ی مرحله‌ها (با زدن شماره‌ی مرحله، جزئیات آن)
d   جزئیات مرحله‌ی فعلی
h   راهنمای مرحله‌ی فعلی
```

این‌ها در صفحه‌ی جدا باز می‌شوند و با بستنشان صفحه به حالت قبل برمی‌گردد. وقتی کار طولانی در حال اجراست هم کار می‌کنند.

اگر ترمینال کوچک‌تر باشد، یا این گزینه داده شود، خروجی ساده و پشت سر هم مثل نسخه‌های قبل نشان داده می‌شود:

```bash
./dg_standby_setup.sh --plain
```

با `--verbose` هر مرحله کامل نشان داده می‌شود و زیر آن هر کوئری یا دستور فقط‌خواندنی که اجرا کرده، با جوابش، می‌آید (`· query  ->  answer`). در پایان هم جدول کامل همه‌ی مرحله‌ها نشان داده می‌شود. دستورهایی که چیزی را تغییر می‌دهند همیشه نشان داده می‌شوند، با یا بدون این گزینه. با `--health --verbose` کوئری‌های هر چک زیر خط همان چک می‌آید و خط اول (وضعیت برای مانیتورینگ) تغییری نمی‌کند. لاگ اجرا همیشه همه‌ی کوئری‌ها را با جوابشان دارد.

```bash
./dg_standby_setup.sh --verbose
./dg_standby_setup.sh --health --verbose
DG_VERBOSE=1 ./dg_standby_setup.sh
```

### ۹. دیدن تغییرها

```bash
./dg_standby_setup.sh --show-changes
./dg_standby_setup.sh --show-changes 6.1
```

همه‌ی تغییرهایی را که اسکریپت روی این سرور داده (فایل‌ها، تنظیمات، کاربرها، دیسک‌ها، سرویس‌ها، تغییرهای دیتابیس) همراه با راه برگرداندن هر کدام نشان می‌دهد. با شماره‌ی مرحله، فقط همان مرحله.

### ۱۰. برگرداندن تغییرهای یک مرحله

```bash
./dg_standby_setup.sh --undo 5.1
```

تغییرهای یک مرحله را از آخر به اول برمی‌گرداند و پیش از هر کدام می‌پرسد. فایل فقط وقتی برگردانده می‌شود که هنوز همان چیزی باشد که اسکریپت نوشته بود. چیزی که ممکن است داده داشته باشد هرگز پاک نمی‌شود. تغییرهای سرور اصلی فقط نشان داده می‌شوند.

### ۱۱. راهنمای دستی یک مرحله

```bash
./dg_standby_setup.sh --help-step 6.1
./dg_standby_setup.sh --help-step all
./dg_standby_setup.sh --help-step health
```

می‌گوید یک مرحله را چطور دستی انجام دهید: کجا، با کدام کاربر، چه دستوری، و چه نتیجه‌ای باید دید. دستورها با نام‌های ذخیره‌شده‌ی شما نوشته می‌شوند.
دستورها از ستون اول و بین دو خط افقی چاپ می‌شوند، پس همان‌طور که هستند کپی می‌شوند. توضیح‌های داخل این بخش با # شروع می‌شوند (داخل sqlplus یا rman با --).

### ۱۲. بررسی خودکار سلامت (cron یا monitoring)

```bash
./dg_standby_setup.sh --health
```

بررسی‌های فاز ۱۰ را بدون سؤال و بدون هیچ تغییری انجام می‌دهد و به terminal هم نیاز ندارد. به این ترتیب:

1. خود instance استندبای (اگر بالا نباشد، همان لحظه CRITICAL)
2. مرحله‌ی 10.1: lag انتقال و apply، و اینکه داده از سرور اصلی هنوز می‌رسد یا نه
3. مرحله‌ی 10.2: gap، و اینکه log های گم‌شده هنوز روی سرور اصلی هستند یا نه
4. مرحله‌ی 10.3: آخرین log در دو طرف
5. مرحله‌ی 10.4: redo apply و real-time apply
6. مرحله‌ی 10.5: بلوک‌های NOLOGGING
7. مرحله‌ی 10.6: یکی بودن patch های دو سرور
8. مرحله‌ی 10.8: فضای archived log ها و پاک‌سازی شبانه

اگر یکی از بررسی‌های ۲ تا ۵ مشکل نشان دهد، ۶۰ ثانیه بعد یک بار دیگر بررسی می‌شود.

**خط اول** خروجی، وضعیت است؛ به همان شکلی که سیستم‌های monitoring (مثل Nagios) می‌خوانند، و lag هم به شکل perfdata در آن آمده است:

```
OK - standby PRODDB_STBY, redo apply running; lag: transport 0 s, apply 1 s (limit 300 s); protection MAXIMUM PERFORMANCE | transport_lag=0s;;300;0 apply_lag=1s;;300;0
```

بعد از آن عنوان، برای هر بررسی یک خط، یک خط Data Guard (نقش، حالت باز بودن، protection mode و آخرین log اعمال‌شده)، یادداشت‌ها، و در آخر خط Result با مسیر فایل جزئیات می‌آید. جزئیات در فایل health_<time>.log می‌ماند (۱۴ روز، حداکثر ۵۰۰ فایل). کد خروجی:

```
0 OK   1 WARNING   2 CRITICAL   3 UNKNOWN
```

حالت UNKNOWN یعنی بررسی ممکن نبود: اجرای دیگری در جریان است، این سرور بعد از switchover سرور اصلی شده، یا گزینه اشتباه است.
مقدار lag قابل قبول با تنظیم HEALTH_LAG_MAX عوض می‌شود (پیش‌فرض ۳۰۰ ثانیه، حداقل ۳۰).

بررسی‌های سمت سرور اصلی به کلید ssh کاربر root نیاز دارند (مرحله‌ی 9.9، پایین‌تر). بدون کلید، سرور اصلی **بررسی نمی‌شود** و این نتیجه را UNKNOWN نمی‌کند:
بررسی‌های 10.3 و 10.5 فقط از سمت استندبای انجام می‌شوند (آخرین log رسیده در برابر آخرین log اعمال‌شده، و فهرست بلوک‌های NOLOGGING خود استندبای)، بررسی 10.6 با وضعیت SKIPPED می‌آید، و یک خط یادداشت می‌گوید:

```
primary not checked: no ssh key for root ...
```

خطاهای دیگر ssh (جواب ندادن سرور، عوض شدن کلید میزبان) همچنان برای همان بررسی‌ها UNKNOWN می‌دهند.

#### بررسی روزانه با cron

بررسی روزانه همین گزینه است (از cron یا monitoring). برای اجرای دستی با صفحه و سؤال‌ها:

```bash
./dg_standby_setup.sh --only 10
```

نمونه‌ی cron برای root روی استندبای. خروجی به هشدار داده می‌شود، چون خط اولش وضعیت است:

```
17 6 * * *  out=$(/root/dg_standby_setup.sh --health) || /usr/local/bin/my-alert "$out"
```

خروجی را به dev/null نفرستید، وگرنه هشدار نمی‌گوید چه چیزی خراب است. در خط crontab علامت درصد باید به شکل \% نوشته شود (خط بالا درصد ندارد).
برای agent های monitoring (مثل NRPE) دست‌کم ۳۰۰ ثانیه وقت بگذارید، چون یک مشکل دو بار با فاصله‌ی ۶۰ ثانیه بررسی می‌شود.

#### کلید ssh برای بررسی سرور اصلی (مرحله‌ی 9.9)

از cron نمی‌شود رمز تایپ کرد، پس بررسی سلامت با یک کلید root به سرور اصلی وصل می‌شود.
مرحله‌ی 9.9 این کلید را می‌سازد (فایل dg_health_<standby unique> در پوشه‌ی root/.ssh، از نوع ed25519، بدون passphrase، با mode 600) و خط دقیقی را که باید روی سرور اصلی گذاشت نشان می‌دهد.
این مرحله اختیاری است. اگر از آن بگذرید، بررسی سلامت فقط استندبای را بررسی می‌کند. برای انجامش در زمان دیگر:

```bash
./dg_standby_setup.sh --only 9.9
```

روش دستی. اول روی استندبای با کاربر root:

```bash
ssh-keygen -q -t ed25519 -N '' -C 'dg_standby_setup health stby01' -f /root/.ssh/dg_health_proddb_stby
cat /root/.ssh/dg_health_proddb_stby.pub
```

بعد روی سرور اصلی با کاربر ssh (معمولاً oracle). یک خط: آدرس استندبای، و بعد کل خط فایل pub:

```bash
mkdir -p ~/.ssh
chmod 700 ~/.ssh
echo 'from="192.0.2.20",no-port-forwarding,no-X11-forwarding,no-agent-forwarding,no-pty ssh-ed25519 AAAA... dg_standby_setup health stby01' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys
```

در آخر روی استندبای با root آزمایش کنید. باید بدون پرسیدن رمز OK چاپ کند:

```bash
ssh -i /root/.ssh/dg_health_proddb_stby -o BatchMode=yes \
  -o UserKnownHostsFile=/var/lib/dg_standby_setup/primary_known_hosts oracle@192.0.2.10 echo OK
```

گزینه‌ی from باعث می‌شود کلید فقط از آدرس استندبای پذیرفته شود. گزینه‌ی no-pty و گزینه‌های no-forwarding به آن نه terminal می‌دهند و نه تونل.
وقتی فایل کلید وجود داشته باشد، بررسی سلامت از همان استفاده می‌کند (با IdentityFile و BatchMode، و با همان بررسی کلید میزبان که در راه‌اندازی انجام شد).
برای برگرداندن: آن خط را روی سرور اصلی پاک کنید و روی استندبای این را اجرا کنید:

```bash
./dg_standby_setup.sh --undo 9.9
```

### ۱۳. به‌روزکردن استندبای عقب‌مانده

```bash
./dg_standby_setup.sh --roll-forward
```

وقتی استندبای عقب افتاده و archived log هایی که لازم دارد روی سرور اصلی پاک شده‌اند، یا بعد از کار NOLOGGING، به‌جای کپی دوباره‌ی کل دیتابیس فقط تغییرها را از سرور اصلی می‌کشد (از 18c به بعد).
رمز sys و کلمه‌ی ROLLFORWARD را می‌پرسد و هرگز با گزینه‌ی yes یا check اجرا نمی‌شود.
پیش از شروع این‌ها را بررسی می‌کند و با هر شکی متوقف می‌شود:

1. استندبای mount باشد.
2. جلسه‌ی RMAN دیگر یا کار طولانی در جریان نباشد.
3. broker خاموش باشد.
4. listener برای استندبای ورودی static داشته باشد.
5. اگر دیتابیس رمزگذاری‌شده است، wallet همه‌ی container ها خودکار باز شود.
6. RMAN به هر دو دیتابیس وصل شود.
7. RMAN بعد از کار فایل‌های استندبای را دوباره پیدا کند. یعنی یا نام فایل‌ها یکی باشد، یا پارامتر زیر نام همه‌ی فایل‌ها را درست تبدیل کند، یا فایل‌ها OMF باشند:

```
db_file_name_convert
```

بعد از کار، standby redo log ها و تنظیم‌های RMAN را دوباره درست می‌کند و redo apply را راه می‌اندازد. اگر وسط کار terminal بسته شود، اجرای بعدی همین فرمان نتیجه را بررسی می‌کند و بعد از تایپ دوباره‌ی ROLLFORWARD کار را تمام می‌کند، بدون اجرای دوباره‌ی RMAN. روی 12.1 و 12.2 فقط راه دستی را نشان می‌دهد.
پیش از اجرا روی production، یک بار روی یک استندبای تستی امتحانش کنید.

## تست‌ها

بیش از ۵۲۰ سناریو روی محیط شبیه‌سازی‌شده تست شده است.
تست‌ها به کاربر روت نیاز دارند و مخرب هستند: پردازه‌های کاربران oracle و grid را می‌بندند، خود این کاربران را با پوشه‌ی خانگی‌شان و گروه‌های اوراکل حذف می‌کنند، و فایل‌های `/etc/hosts` و `/etc/oratab` و `/etc/oraInst.loc` را تغییر می‌دهند یا پاک می‌کنند.
برای همین فقط باید داخل یک کانتینر یا ماشین مجازی یک‌بارمصرف اجرا شوند، هرگز روی سروری که اوراکل دارد.
مجموعه‌ی تست روی ماشینی که شبیه سرور واقعی اوراکل باشد شروع نمی‌شود.

محیط شبیه‌سازی‌شده اوراکل واقعی نیست.
پیش از استفاده روی محیط عملیاتی، حتماً اسکریپت را روی سرورهای واقعی در حالت بررسی اجرا کنید و گزارشش را بخوانید.

## محدودیت‌های شناخته‌شده

1. اسکریپت فقط روی محیط شبیه‌سازی‌شده تست شده و هنوز از ابتدا تا انتها روی سرور واقعی اجرا نشده است. اول حالت بررسی را اجرا کنید.
2. نسخه‌های ۲۱ و ۲۳: خانه‌ی اوراکل فقط‌خواندنی است و اسکریپت هنوز خانه‌ی خواندنی‌نوشتنی می‌خواهد (مرحله‌ی ۳.۸).
3. کلید بررسی سلامت (مرحله‌ی ۹.۹) به کاربر روتِ استندبای اجازه می‌دهد بدون رمز با کاربر اوراکلِ سرور اصلی وارد شود. از روتِ استندبای مراقبت کنید.
4. بعد از سوییچ‌اور، پاک‌سازی شبانه‌ی آرشیولاگ‌ها دیگر چیزی پاک نمی‌کند. بدون گرید، سرویس زمان بوت دیتابیس را فقط تا حالت مانت بالا می‌آورد.
5. اسکریپت چک‌سام درست فایل‌های نصب را نمی‌داند. مرحله‌ی ۳.۱ مقدار SHA-256 هر فایل را چاپ می‌کند؛ پیش از نصب، آن را با مقدار صفحه‌ی دانلود اوراکل مقایسه کنید.
